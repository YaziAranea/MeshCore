# SmartUI 0.14 Local CLI SDK

Локальные CMD66/RESP29 для настроек подключённой ноды. Текущая прошивка сообщает
companion protocol 14; прежние SmartUI с protocol 13 сохраняют свои `ui`-команды.
SDK не работает с удалённой LoRa-CLI и не поддерживает API201, sync/events
из SmartUI 0.11.

[Русская спецификация](../../docs/SMARTUI_CLI_RU.md).
Обычному пользователю достаточно USB Helper 1.8.

## Состав

- `smartui_cli.py`: кодек и последовательный клиент с prefix correlation.
- `transports.py`: явные USB/TCP адаптеры; TCP использует только стандартную библиотеку.
- `inspect_device.py`: пример только для чтения, без автоматического поиска устройств.
- `../../tools/usb-helper/api.js`: общий JS-кодек и Web Serial клиент, UMD/CommonJS.
- JS-фикстура и тесты включены в Developer Kit. Готового npm/TypeScript-пакета нет.
- Каталог городов `../../tools/usb-helper/presets.js` и [описание источника](../usb-helper/PRESETS_SOURCE_RU.md). Обновление снимка — отдельная явная команда разработчика, не запрос при подключении ноды.

## Проверки без устройства

Из корня репозитория или распакованного Developer Kit:

~~~sh
python -B -m unittest discover -s tools/smartui-cli/tests -v
node --test tools/usb-helper/test_api.js
~~~

Тесты не открывают реальные USB/BLE/TCP и не означают проверку физической платы.

## Подключение только по явному выбору

Закройте другое приложение, владеющее тем же портом. Для USB выберите на ноде
USB-компаньон, не сервисную консоль. USB требует необязательный пакет `pyserial`,
установленный пользователем; SDK ничего не устанавливает сам.

~~~sh
python tools/smartui-cli/inspect_device.py --usb COM6
python tools/smartui-cli/inspect_device.py --tcp 192.168.1.60 --port 5000
~~~

Это примеры адресов, не указание подключиться к ним. TCP не имеет отдельной
аутентификации/TLS: только доверенная LAN. Не открывайте порт в интернет.
BLE адаптер здесь не поставляется: интегрируйте кодек в общую очередь существующего
BLE клиента, с одним читателем и целыми companion-кадрами подходящего MTU.

## Встраивание Python

~~~python
from smartui_cli import CliClient
import transports

transport = transports.usb("COM6")  # Только после выбора пользователем.
client = CliClient(transport.exchange, transport.close)
try:
    hello = client.connect()  # CMD22/40, marker smartui_cli:1, ui hello.
    print(client.field("get", "volume"))
    # Запись только после подтверждения пользователя:
    # client.execute("ui set volume 5")
    # assert client.field("get", "volume") == "5"
finally:
    client.close()
~~~

`CliClient` не повторяет команды. Тайм-аут означает неизвестный результат:
закройте транспорт, создайте новое подключение и перечитайте состояние.
`ERR ui unsupported` можно пропустить для необязательного поля; readonly не
обходить. Префиксы не переиспользуются в сессии. Не запускайте второй клиент
поверх того же stream и не выводите сырой ответ, команды с паролем или DeviceInfo.

## Встраивание JavaScript

~~~js
const {encodeCommand, decodeReply, matches} = require('../usb-helper/api.js');
const request = encodeCommand('a9', 'ui get volume');
// Передайте request своей ЕДИНОЙ очереди companion; не создавайте второй reader.
// Когда совпал matches(request, response):
// const text = decodeReply(response, 'a9');
~~~

В браузере тот же файл создаёт `SmartUiCli`. `CliClient` владеет Web Serial портом
целиком; для уже работающего приложения используйте кодеки в его собственной очереди.
Теги выбирайте уникально на всю сессию, не копируйте постоянный `a9` из примера.
`decodeReply` допускает UTF-8 штатных команд только с третьим аргументом `false`;
для `ui` оставляйте проверку ASCII.

Общие требования к клиентской реализации приведены в спецификации.
SDK не привязан к конкретному приложению или стороннему репозиторию.

## Команды оригинального MeshCore

Дополнительный признак `meshcore=1` в `ui hello` разрешает следующий **закрытый
список** команд. Один номер протокола 14 не заменяет эту проверку. Если признака
нет, новые команды отклоняются локально; прежние `ui`, `board`, `ver`, `get name`
и `get radio` продолжают работать.

- Чтение: `get freq`, `get tx`, `get af`, `get dutycycle`, `get rxdelay`,
  `get multi.acks`, `get path.hash.mode`, `get radio.rxgain`, `get tz.offset`,
  `get wifi.status`, `get wifi.ip`.
- Запись: `set name`, `set pin`, `set tx`, `set af`, `set dutycycle`, `set rxdelay`,
  `set multi.acks`, `set path.hash.mode`, `set radio.rxgain`, `set tz.offset`,
  `set radio FREQ_MHZ,BW_KHZ,SF,CR`. Параметр после имени команды обязателен.
- Все `set` автоматически считаются изменениями: `write=0` запрещает отправку.
  Ограничения конкретной платы и диапазоны проверяет прошивка.

~~~python
hello = client.connect()
if hello.get("meshcore") == "1":
    print(client.execute("get tx"))  # Например, "> 20".
    # Только после подтверждения пользователя:
    # assert client.execute("set name Дача") == "OK"
    # assert client.execute("get name") == "> Дача"
~~~

JavaScript `CliClient.execute(...)` использует те же команды и проверки. Если
приложение использует только `encodeCommand`/`decodeReply` без клиента, оно само
проверяет `meshcore=1`, `write=1`, управляет одной очередью и выполняет readback.
Для штатного ответа у `decodeReply(response, tag, false)` нужен третий аргумент
`false`; `ui` по-прежнему использует ASCII. UTF-8 допускается при вводе имени:
вся команда с префиксом должна помещаться в 160 байт; прошивка ограничивает имя
31 байтом. Непарные суррогаты, управляющие символы и неизвестные команды запрещены.

`Error, …`, `Error: …` и `ERROR: …` вызывают исключение без публикации сырого
текста. Возвращённую строку успеха проверяет вызывающее приложение, затем читает
изменённый параметр обратно. Исключение не означает успешного сохранения. PIN
может присутствовать в штатном ответе `set pin`; не выводите и не журналируйте его.

`reboot`, `poweroff`, `shutdown` сознательно **не входят в SDK**: прошивка может
закрыть соединение без ACK, поэтому клиент не может достоверно подтвердить успех.
Для собственной реализации таких действий нужен отдельный завершающий сценарий:
отправка один раз, закрытие сессии, неизвестный результат до повторного подключения.
Автоматический повтор и произвольный raw/rescue fallback здесь не предусмотрены.
Wi-Fi настраивается через `ui wifi`; чтение пароля и `set wifi.*` не разрешаются.

## Радио и автоанонс с 0.13

Через тот же `client.execute(...)` доступны `ui radio` и `ui advert`.
Они читают радиопараметры и интервал автоанонса; на 0.12 эти команды отсутствуют.
После отдельного подтверждения пользователя можно отправить
`ui radio set FREQ_KHZ BW_HZ SF CR PATH_BYTES` или `ui advert set MINUTES`.
Перечитайте результат, не повторяйте изменение при тайм-ауте. Полные единицы,
допустимые интервалы, ошибки и требования сохранения описаны в спецификации.

## Сервисное окно ADC с 0.14

Обновлённый 0.14 также поддерживает прямой ввод коэффициента. Проверьте
`record(client.execute("ui adc manual"), "OK ui adc_manual")["supported"]`:
нужен `"1"`. На раннем 0.14 команда может отвечать `invalid`/`unsupported`,
поэтому одного номера версии недостаточно. После подтверждения пользователем
можно вызвать `client.execute("ui adc set 1.815000")` и проверить
`client.field("get", "adc_multiplier")`. Число здесь — пример, не рекомендация
для любой платы. Прямой ввод не требует опорного замера от АКБ; диапазон и
защита записи не меняются. На проводе используется точка, максимум 6 дробных
цифр. При потере ответа не повторяйте запись автоматически.

Сначала проверьте `client.field("caps", "adc_service")`. Значение `1` означает
поддержку, но не подтверждает текущее USB-питание. На старой прошивке возможен
`invalid` или `unsupported` именно для нового ключа: обычная калибровка при этом
остаётся доступной. Не трактуйте любые ошибки других команд как отсутствие функции.

`client.execute("ui adc service")` читает состояние; ответ разбирается через
`record(reply, "OK ui adc_service")`. Поля: `supported`, `active`, `remaining_ms`,
`external`. Только после отдельного предупреждения и подтверждения пользователя
допустим `ui adc service start`: максимум 120 секунд при подтверждённом USB
и локальном USB-компаньоне. BLE/TCP получат `ERR ui usb_required`; SDK сохраняет
точную причину в `CliError.reason`. Повтор активной команды не продлевает окно.

`ui adc service stop` доступен даже при `write=0`, как и чтение состояния.
Не повторяйте start после тайм-аута. Переподключитесь и перечитайте состояние.
Окно завершается при потере USB/сеанса, успешном сохранении/сбросе ADC, истечении
таймера или ручном stop; запрет записи и требования свежего замера не обходятся.
