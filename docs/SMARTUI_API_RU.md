# SmartUI 0.10 API v1 — руководство разработчика

API v1 предназначен для SmartUI 0.10. Проверяйте `smartui_api:1` и ответ `HELLO`,
а не только номер прошивки. Документация описывает интерфейс; наличие файлов
и пройденных тестов не означает публикацию прошивки. Модульные тесты и сборка
не заменяют проверку на физических устройствах.

## Что доступно

API добавляет отдельный бинарный конверт к существующему протоколу companion.
Базовые команды MeshCore, радиообмен и формат обычных сообщений не заменяются.
Через API можно читать возможности платы, настройки и состояние подключения;
при разрешённой записи — менять поддерживаемые настройки и калибровать АЦП.

В этой версии:

- BLE, USB и Wi-Fi/TCP поддерживают чтение и запись с существующими guards
  восстановления/хранилища. Реальные права сообщает `write` в HELLO.
- TCP не получает новую аутентификацию или TLS. Клиент с сетевым доступом может
  менять настройки, если guards разрешают запись. Используйте доверенную сеть;
  не открывайте порт устройства в Интернет.
- Wi-Fi настраивается через staged API по BLE/USB с тестом до сохранения.
  Тестировать новую сеть через тот же TCP-сеанс нельзя: смена сети оборвёт его.
  Это ограничение непрерывности сессии, а не отдельная авторизация.
- Смена режима соединения доступна через API; bridge — при `caps.bridge=1`.
  Существующие USB helper и локальный интерфейс также остаются доступны.
- Событий и подписок пока нет: `events=0`. Это направление следующих версий,
  а не скрытая команда текущей версии.

## Начало сессии и обнаружение

1. Выберите транспорт на устройстве. BLE должен пройти обычную процедуру доступа;
   USB должен находиться в бинарном companion-режиме, не в текстовой консоли.
   Для Wi-Fi заранее настройте сеть; TCP использует существующий listener.
2. Выполните обычное согласование companion. Пример SDK для нового USB/TCP-сеанса
   посылает `CMD_DEVICE_QUERY` — байты `[22, 3]`. В чужой уже работающей сессии
   не повторяйте согласование без координации с её владельцем.
3. Посылайте `CMD_GET_CUSTOM_VARS`, один байт `40` (`0x28`). Ожидаемый код ответа
   — `21` (`0x15`); далее идут разделённые запятыми пары `имя:значение`.
4. Найдите отдельную пару `smartui_api:1`. Отсутствие, иная версия или неоднозначные
   дубликаты означают: API не использовать. Не проверяйте stock-прошивку слепой
   отправкой неизвестного ей opcode `0xC9`.
5. Отправьте API `HELLO`, затем `api caps`, `api get`, `api connection`.

Не публикуйте полные дампы companion-сеанса: стандартный `DEVICE_INFO`, например,
содержит поле BLE PIN. SDK не печатает этот пакет. Диагностические журналы должны
содержать только необходимые и проверенные на отсутствие секретов данные.

## Транспорт: где заканчивается кадр

| Транспорт | Host → device | Device → host |
| --- | --- | --- |
| BLE UART service | Сам companion-пакет в RX characteristic | Сам companion-пакет в TX notification |
| USB / TCP | `0x3C` (`<`), `length:uint16 LE`, пакет | `0x3E` (`>`), `length:uint16 LE`, пакет |

`length` считает только содержимое companion-пакета, без трёх внешних байтов.
Максимальный обычный companion-пакет — 176 байт, его USB/TCP envelope — до 179 байт.
API v1 использует более узкий лимит: 160 байт пакета, до 163 с USB/TCP envelope.
Числа LE записываются младшим байтом вперёд. Разделителей строк и завершающего NUL
в бинарных API-командах нет.

TCP — поток: один `recv()` не равен одному кадру. Кадр может прийти по одному
байту; один `recv()` может содержать несколько кадров. Декодер должен сохранять
неполный заголовок/пакет и извлекать все завершённые кадры. Не смешивайте сырые
строки USB-консоли с бинарным обменом. SDK при неожиданном тексте останавливается,
а не пытается угадать границу валидного ответа.

BLE service: `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`;
запись RX: `6E400002-B5A3-F393-E0A9-E50E24DCCA9E`;
уведомления TX: `6E400003-B5A3-F393-E0A9-E50E24DCCA9E`.
Доставка должна сохранять целый companion-пакет. Для API-уведомления из 160 байт
нужен фактически согласованный ATT MTU не менее 163 байт. Поддержку нельзя
выводить только из запрошенного MTU. Самовольно дробить API-пакет на несколько
GATT write нельзя: прошивка воспринимает записи как отдельные companion-кадры.
BLE-адаптер не входит в Python SDK; используйте dispatcher существующего
BLE-клиента и отдельно проверьте MTU/notification delivery на целевой плате.

## Бинарный API-конверт

Общий префикс: `C9 53 55 49 01`, то есть `0xC9`, ASCII `SUI`, версия `1`.
Все `uint16` ниже — little-endian.

### Запрос

| Смещение | Размер | Поле |
| --- | ---: | --- |
| 0 | 1 | `0xC9` |
| 1 | 3 | ASCII `SUI` |
| 4 | 1 | Версия `1` |
| 5 | 2 | `request_id`, 1…65535 |
| 7 | 1 | Операция |
| 8 | 0…152 | Данные операции |

Операции:

- `0 HELLO`: данных нет; новый ID.
- `1 EXEC`: команда длиной 1…152 байта, только printable ASCII `0x20…0x7E`.
  Включайте префикс `api `; без `\n`, `\r`, NUL и UTF-8 в командах.
- `2 READ_PAGE`: ровно два байта `offset:uint16 LE`; ID последнего HELLO/EXEC.

Пример HELLO с ID `0x1234`:

```text
C9 53 55 49 01 34 12 00
```

Пример `api get`, ID `2`, с внешним USB/TCP envelope:

```text
3C 0F 00 C9 53 55 49 01 02 00 01 61 70 69 20 67 65 74
```

### Ответ

| Смещение | Размер | Поле |
| --- | ---: | --- |
| 0 | 5 | `C9 53 55 49 01` |
| 5 | 2 | ID запроса |
| 7 | 1 | Операция запроса, включая `2` для READ_PAGE |
| 8 | 1 | Status |
| 9 | 2 | Смещение данных в полном ответе |
| 11 | 2 | Полная длина текстового ответа |
| 13 | 0…147 | ASCII-фрагмент ответа |

Полный текст ответа ограничен 479 байтами (`max_reply=479`). Реализация хранит
его в 480-байтном буфере вместе с NUL.
NUL по проводу не передаётся. Первое смещение — `0`; пока накопленная длина меньше
`total`, запросите READ_PAGE со смещением накопленной длины. При полном первом
фрагменте это `147`, затем `294` и при необходимости `441`. ID не меняется. Не задавайте отрицательные
смещения, смещение за пределами ответа или смещение, не дающее следующего байта.
Для новой команды нужен новый ID; её ответ заменяет прежний кэш.

Проверяйте magic, версию, ID, операцию, status, точное ожидаемое смещение,
неизменность `total` и отсутствие превышения границ на каждой странице.
Неуспешный transport-status не превращается в успех из-за текста ответа.

### Status

| Код | Значение | Действие клиента |
| ---: | --- | --- |
| 0 | OK | Разобрать полный `OK api ...` |
| 1 | Malformed | Исправить форму/длину кадра |
| 2 | Bad version | Не использовать неподдерживаемую версию |
| 3 | Unknown operation | Не повторять неизвестную операцию |
| 4 | Busy | Не запускать конкурирующие запросы; повторять осознанно |
| 5 | Denied | Проверить транспорт, доступ и read-only; не обходить guard |
| 6 | Stale / ID conflict | Проверить ID, сессию и кэш; не повторять запись под новым ID автоматически |
| 7 | Command failed | Разобрать `ERR api CODE`, проверить причину |

Ошибка может не содержать текста. Клиент обязан сохранить числовой status.
Типичные доменные причины: `invalid`, `range`, `unsupported`, `readonly`,
`measurement`, `stale`, `storage`, `unavailable`, `internal`.
Настройка подключения дополнительно использует `transport`, `unconfigured` и `buffer`.
Полученный явно `busy` — известный отказ, не таймаут. Он также кэшируется:
тот же ID вернёт тот же `busy`. После устранения занятости оператор может
осознанно отправить новую попытку с новым ID; автоматической петли повторов нет.

## Сессия, ID и повтор без повторного выполнения

Новые HELLO и EXEC используют строго возрастающие ID 1…65535. После 65535
откройте новую сессию; не переходите к 1 внутри прежней. Один dispatcher должен
координировать все API-запросы сессии. Параллельные запросы не поддерживаются.

Повтор **последнего** HELLO/EXEC с тем же ID и теми же байтами возвращает
закэшированный ответ, не повторяя запись или иной side effect. Старый ID либо
последний ID с другой командой отклоняется. READ_PAGE работает только с ID
последнего запроса. После следующей новой команды повтор прежней уже не гарантирован.

Таймаут означает «результат неизвестен», а не «команда не выполнена»:

1. Не создавайте новый ID для автоматического повтора записи.
2. Пока та же сессия жива, повторите исходный кадр без изменений.
3. Если потеряна связь, повтор с прежним ID после reconnect уже не защищён:
   сессионный кэш очищен. Сначала прочитайте текущее состояние, затем согласуйте
   с оператором необходимость нового действия. Для тестового звука чтение
   настроек не доказывает, был ли звук уже воспроизведён.

Смена USB-консоли сама по себе не должна инвалидировать transport-cache API.
Фактическое отключение/новая сессия инвалидирует его. Кэш ответа и токен
ADC preview — разные механизмы: соблюдайте отдельный срок и условия токена.

SDK ничего не повторяет автоматически. После timeout/OSError/невалидного
ответа он блокирует новую команду до `retry_last()` либо явного завершения
сессии. Если потерялся не первый ответ, а страница, `retry_last()` заново читает
первую кэшированную страницу того же запроса и затем остальные.

## HELLO и capabilities

HELLO возвращает ASCII-запись со следующими полями; порядок не является API:

```text
OK api hello v=1 firmware=0.10 stage=release max_command=152 max_reply=479 max_frame=160 transport=ble|usb|wifi write=0|1 events=0 wifi_setup=0|1
```

Это схема, не буквальные значения `ble|usb|wifi` и `0|1`.
`write` — разрешение текущей сессии, а не наличие аппаратной функции.
`wifi_setup=1` сообщает поддержку Wi-Fi setup в текущем BLE/USB-сеансе;
для TCP или платы без Wi-Fi — `0`.
`api caps` сообщает поддержку функций платы:

```text
v adc sound board_led unread_led vibration gps battery_protection display
melody_max adc_min adc_max agc_reset fem_lna fem_pa bridge melody_names
```

Значения приходят как `key=value`. Поддержка функций, включая `bridge`, — `0/1`.
`melody_max` — включительная верхняя граница номера мелодии.
`adc_min`/`adc_max` — границы множителя АЦП, а не напряжение батареи.
Перед построением UI или записью проверяйте capability, а не название платы.
Неизвестные дополнительные поля сохраняйте или игнорируйте; не отклоняйте
совместимый ответ только из-за добавленного поля.

## Команды и значения

| Команда | Результат / ограничение |
| --- | --- |
| `api caps` | Возможности платы и границы значений |
| `api get` | Снимок настроек и измерения |
| `api connection` | Санитизированная информация о выбранном и текущем транспорте |
| `api melody N` | Название мелодии: `id=N name_hex=...`, не проигрывает звук |
| `api set KEY VALUE` | Проверка capability/диапазона, сохранение и применение |
| `api adc preview N` | N — измеренное внешним прибором напряжение в мВ; выдаёт токен, ничего не сохраняет |
| `api adc apply TOKEN` | Сохраняет предложенный множитель при действительном токене |
| `api adc reset` | Возвращает штатный множитель АЦП |
| `api test` | Физическая проверка поддерживаемых уведомлений; это действие, не чтение |
| `api wifi ...` | Staged настройка Wi-Fi; см. отдельный раздел |
| `api mode ble\|usb\|wifi` | Отложенная смена транспорта после ответа; может разорвать сессию |

Перед изменением требуются `write=1` и подходящий capability. TCP поддерживает
обычные записи, но не тест/сохранение новых Wi-Fi credentials через текущий TCP-сеанс.

Ключи `api set`:

| Ключ | Значения | Capability |
| --- | --- | --- |
| `sound_quiet` | `0/1`; 1 отключает звук уведомлений ЛС | `sound` |
| `volume` | 1…10 | `sound` |
| `melody` | 0…`melody_max` | `sound` |
| `board_led` | 0/1 | `board_led` |
| `unread_led` | 0/1 | `unread_led` |
| `vibration` | 0/1 | `vibration` |
| `gps` | 0/1; выбирает аппаратный GPS как источник | `gps` |
| `battery_protection` | 0/1 | `battery_protection` |
| `muted` | 0/1 | Общий флаг; соблюдается read-only guard |
| `agc_reset` | 0/1 | `agc_reset` |
| `fem_lna` | 0/1 | `fem_lna` |
| `fem_pa` | 0/1 | `fem_pa` |
| `bridge` | 0/1 | `bridge` |

`bridge` доступен только при соответствующем capability. `battery_protection` влияет на защиту батареи;
`gps`, усилители и уведомления — на потребление. SDK-примеры по умолчанию ничего
из этого не меняют. Успешные настройки сохраняются; ошибка `storage` означает,
что нельзя показывать пользователю сообщение об успешной записи.
`melody` задаёт одну выбранную мелодию для всех типов уведомлений. Запись
`muted` также снимает отдельный флаг `night_quiet`. Эти настройки переводят
профиль в пользовательский; это не независимые временные UI-переключатели.

`api get` содержит `battery_mv`, `adc_multiplier`, `adc_default`, `sound_quiet`,
`volume`, `melody`, `board_led`, `unread_led`, `vibration`, `gps`,
`battery_protection`, `shutdown_mv`, `muted`, `agc_reset`, `fem_lna`, `fem_pa`, `bridge`.
Данные описывают текущее состояние с учётом реализации платы; нулевое значение
не заменяет проверку capability.

`api connection` содержит поля `selected`, `via`, `caps`, `wifi_configured`,
`wifi_associated`, `ip`, `readonly`: выбранный режим, фактический транспорт
запроса, возможности транспорта, конфигурация/ассоциация Wi-Fi, IP и read-only.
Настройка сети вынесена в `api wifi ...`. SSID, пароль, PIN и credentials
в ответ не включаются. `selected` и `via` не следует считать синонимами.
`caps` здесь — десятичная битовая маска транспорта: BLE=`1`, USB=`2`, Wi-Fi=`4`;
проверяйте биты, например `int(record["caps"]) & 4`. Это не запись `api caps`.
`selected` использует `ble`, `usb`, `wifi`; `via` дополнительно может быть `none`.
`wifi_configured`, `wifi_associated`, `readonly` — `0/1`; отсутствующий IP — `none`.

### Мелодии и UTF-8

`api melody N` возвращает название в `name_hex`, hex-кодировании UTF-8.
Сначала проверяйте hex и декодируйте байты, затем UTF-8. В интерфейсе используйте
название как текст, не как HTML. Диапазон берите из `melody_max`;
`melody_names=0` означает отсутствие этого механизма на данной сборке/плате.

### АЦП: только после измерения

Измерьте напряжение батареи подходящим внешним прибором. Не подставляйте число
из примера или само показание устройства вместо измерения.

1. Прочитайте caps/get и убедитесь в `adc=1`, `write=1`.
2. Отправьте `api adc preview N`, где N — целое число мВ, 2500…4500.
3. Покажите оператору `sampled_mv`, `measured_mv`, `multiplier`; не применяйте
   предложение автоматически.
4. После подтверждения отправьте `api adc apply TOKEN` в течение 60 секунд,
   пока исходные ADC-настройки не изменились. При `stale` получите новый preview.
5. Повторно прочитайте `api get`, проверьте сохранённый результат.

Новая калибровка ограничена допустимым диапазоном множителя. `preview` не
сохраняет настройки, но создаёт временный токен. Успешное изменение настроек
может сделать прежний preview недействительным. `api adc reset` — отдельное
осознанное действие, не автоматическая обработка ошибки.

## Wi-Fi: staged настройка без потери старой сети

Команды изменения Wi-Fi выполняются через BLE или USB. На активном Wi-Fi/TCP
они возвращают `ERR api transport`: тест другой сети оборвёт канал, по которому
клиент должен подтвердить сохранение. Остальные записи настроек по TCP разрешены
при `write=1`. Это не требование новой аутентификации.

| Команда | Назначение |
| --- | --- |
| `api wifi status` | Только состояние; доступно через любой транспорт |
| `api wifi begin` | Начать транзакцию текущей сессии; прежняя конфигурация не меняется |
| `api wifi ssid HEX` | SSID в hex байтов UTF-8, 1…32 байта после декодирования |
| `api wifi password HEX` | Пароль в hex: 8…63 байта либо 64 ASCII hex-символа PSK после декодирования |
| `api wifi password -` | Явно выбрать открытую сеть без пароля |
| `api wifi test` | Начать асинхронный тест кандидата, не сохранять |
| `api wifi save` | Сохранить только успешно проверенного и ещё ассоциированного кандидата |
| `api wifi cancel` | Отменить свою транзакцию, очистить временные credentials |

Hex — обратимое кодирование, **не шифрование**. Не пишите SSID, пароль, hex,
сырые API-кадры или `last_request` в логи/аналитику/историю команд. Не передавайте
пароль аргументом командной строки. API не возвращает пароль или SSID ни в одном
ответе. Вход запрещает NUL, управляющие байты и DEL; пределы считаются в байтах,
не символах. До `save` конфигурация на диске не меняется.
64-символьный PSK также передаётся во внешнем hex-кодировании, то есть 128
символами payload; 64 произвольных не-hex символа не являются валидным паролем.

Порядок: `begin` → `ssid` → `password` → `test` → опрос `status` → подтверждение
пользователя → `save`. Состояния: `ssid`, `password`, `ready`, `testing`, `test_ok`;
терминальные результаты: `saved`, `failed`, `timeout`, `cancelled`, обычное `idle`.
Подключение тестируется до 15 секунд. После 120 секунд без шага транзакции она
отменяется; один только опрос status срок не продлевает. Разрыв сессии также
отменяет setup и очищает кандидата. Повтор шагов под тем же request ID обрабатывает
общий replay-cache; для нового шага нужен новый ID.

`status` возвращает `state owner supported configured associated ip ssid_set
password_set mode_pending last_mode_error`. `owner` — `api`, `console` или `none`;
два wizard одновременно не работают. `ssid_set/password_set` — только готовность
полей, не их содержимое; `password_set=1` может означать явно выбранную открытую
сеть. `configured=1` описывает сохранённую конфигурацию, а не факт сохранения
текущего кандидата. При тесте `associated=1` может относиться к кандидату.

При неверном порядке — `stale`; конкурирующем wizard — `busy`; read-only —
`readonly`; неподдерживаемой плате — `unsupported`. При `storage` прежняя
конфигурация сохраняется; кандидат может быть повторно сохранён до таймаута,
если storage guard всё ещё разрешает запись. После потери ассоциации `save`
возвращает `stale`. Не подменяйте
успешную проверку автоматическим сохранением непроверенных credentials.

SDK предоставляет одноимённые методы. Пароль запрашивайте скрытым полем приложения
или `getpass.getpass()`, а не вставляйте литералом в программу:

```python
import getpass

api.wifi_begin()
api.wifi_ssid(input("SSID: "))
api.wifi_password(getpass.getpass("Пароль; пустой для открытой сети: "))
api.wifi_test()
# Опрос api.wifi_status() в event loop приложения, например раз в секунду.
# Только после state=test_ok и отдельного подтверждения пользователя:
# api.wifi_save()
# Для отмены незавершённого setup: api.wifi_cancel()
```

Не запускайте `save` сразу после `test`: операция асинхронна. SDK не сохраняет
самостоятельно. Python не гарантирует secure erase неизменяемых строк/bytes;
не храните введённый пароль дольше необходимого и не дампите память процесса.

## Смена транспорта

`api mode ble`, `api mode usb`, `api mode wifi` возвращает
`OK api mode target=... state=pending`; уже выбранный режим — `state=active`.
Для Wi-Fi требуется ранее сохранённая сеть, иначе `ERR api unconfigured`.

`pending` означает постановку в очередь, **не окончательное применение**.
Прошивка ждёт успешной постановки ответа в TX, минимум 100 мс и опустошения
TX-очереди. Если за две секунды это не произошло, смена отменяется, а не выполняется
без ответа. До применения разрыв сессии или переход к read-only тоже отменяет
операцию. Очередь не доказывает, что приложение действительно прочитало ответ.

После применения текущая сессия может оборваться. Подключитесь через новый
транспорт, выполните discovery/HELLO заново и проверьте `api connection`.
Если смена не произошла, `api wifi status` показывает `mode_pending` и
`last_mode_error` (`none`, `timeout`, `cancelled`, `readonly`, `storage`, `apply`).
Сохранение режима выполняется при применении; ошибка хранилища не является
успешной сменой. Не запускайте бесконечное переподключение/повтор записи.

## Python SDK и интеграция в приложение

Файлы: [tools/smartui-api](../tools/smartui-api/README.md). Ядро — Python 3.10+
без внешних библиотек. TCP также stdlib; USB требует отдельно установленный
`pyserial`. Автоматической установки или поиска устройств нет.

Из корня репозитория, после замены параметров на свои:

```sh
python tools/smartui-api/inspect_device.py tcp HOST PORT
python tools/smartui-api/inspect_device.py usb SERIAL_PORT
python -B -m unittest discover -s tools/smartui-api/tests -v
```

Inspector только читает данные. Wi-Fi должен быть уже настроен. Не открывайте один USB-порт одновременно
в helper, терминале и API-клиенте; открытие порта на некоторых платах вызывает reset.

Для собственного companion-клиента:

```python
from smartui_api import SmartUIClient, melody_name

# exchange принимает/возвращает один пакет БЕЗ '<'/'>' и длины.
# Оно уже умеет ждать нужный ответ и передавать обычные push-пакеты приложению.
api = SmartUIClient(exchange)
hello = api.hello()
caps = api.caps()
state = api.get()
connection = api.connection()
if caps.get("melody_names") == "1":
    name = melody_name(api.execute("api melody 0"))
```

`execute()` возвращает полный текст; `caps()`, `get()`, `connection()` — словарь
строк. Для чисел самостоятельно проверяйте тип, диапазон и нужные поля.
SDK не подменяет валидацию прошивки и не обещает конкретные возможности платы.

Пример явно разрешённой записи, не часть read-only inspector:

```python
if hello["write"] != "1" or caps.get("sound") != "1":
    raise RuntimeError("Изменение громкости недоступно в этой сессии")
# Выбранное оператором значение; этот вызов сохраняет настройку.
reply = api.execute("api set volume 5")
updated = api.get()
```

После таймаута не выполняйте `get()` раньше разрешения неопределённого запроса:
новая команда вытеснила бы его кэш. Схема явного повтора:

```python
try:
    reply = api.execute(command_selected_by_operator)
except TimeoutError:
    # Только если подтверждено, что исходная транспортная сессия не прерывалась.
    # Если связь потеряна — завершить сессию и отдельно проверить результат.
    reply = api.retry_last()
```

Не делайте бесконечный цикл retry. `ApiError` хранит `status`, `text`,
`request_id`; `ProtocolError` означает нарушение формата/сопоставления.
`PendingRequestError` защищает от нового ID при неизвестном исходе.

У обычного companion-протокола существуют push-кадры, не относящиеся к API.
Dispatcher должен направлять их штатным обработчикам, а ответ API сопоставлять
по magic + ID + операции + смещению. В `StreamExchange` предусмотрен `on_packet`;
без callback хранится ограниченная очередь `unsolicited` до 64 кадров.
Это не фоновый event loop: очереди обрабатываются во время вызовов exchange.
Для постоянно работающего приложения используйте общий фоновый dispatcher,
а не конкурирующих читателей одного сокета/характеристики.

## Проверка готовности интеграции

- Stock-прошивка без marker не получает `0xC9`.
- Тестируются частичный заголовок, split/coalesced TCP-пакеты, неожиданные push.
- Ответ проверяется до отображения успеха; длинные caps/get собираются полностью.
- Timeout после записи приводит к тому же ID, не к новой записи.
- Разрыв соединения очищает гарантии replay; ID не переносятся слепо между сессиями.
- UI учитывает caps, `write` и `wifi_setup`, не предлагает недоступные функции.
- Проверка ADC требует внешнего измерения и отдельного подтверждения применения.
- BLE MTU, USB console coexistence, staged Wi-Fi setup и смена транспорта
  проверяются на настоящих устройствах перед распространением приложения.
  Здесь такая проверка не заявлена как выполненная.
